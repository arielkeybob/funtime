# Continuidade do FunTime

- Trabalhe e responda em português. Este é o app FunTime 2.0; `balada` permanece como nome do workspace e chave de compatibilidade com dados antigos. Preserve a compatibilidade com arquivos de backup/importação já exportados por versões antigas.
- Use diretamente `C:\xampp\htdocs\balada`. Confira branch, diff e estado Git antes de editar; preserve alterações do usuário. Faça commit e push quando solicitados, sem interpretar exemplos antigos de publicação como autorização atual.
- O remote `origin` apontava para `https://github.com/arielkeybob/intervalo.git` (app v1 "Intervalo", descontinuado — ver docs/specs/0018). Se ocorrer `dubious ownership`, use `git -c safe.directory=C:/xampp/htdocs/balada ...` restrito ao comando; não altere configuração global.
- FunTime em `codex/funtime-v2`: o remote `funtime` aponta para `https://github.com/arielkeybob/funtime.git`. Publicar com `git push funtime HEAD:main`, nunca sobre origin/main. Estado da versão estável em RELEASE-V2.md.
- Leia [README.md](README.md) para o produto, [DEVELOPMENT.md](DEVELOPMENT.md) para arquitetura/testes e [ROADMAP.md](ROADMAP.md) para ideias futuras. [CONTEXT.md](CONTEXT.md) registra a recuperação do histórico e seus limites. Confirme alegações históricas no código.
- A migração de marca v1 ("Intervalo") → FunTime 2 já aconteceu e foi concluída; ninguém mais usa a v1 e o suporte a ela (ponte, transferência de dados, coexistência) foi removido do código (docs/specs/0018-remove-v1-support.md). [MIGRATION-FUNTIME.md](MIGRATION-FUNTIME.md)/[TRANSITION-V2.md](TRANSITION-V2.md) ficam só como registro histórico do que já aconteceu, não descrevem nada vigente.
- Preserve HTML/CSS/JavaScript puro, sem build ou backend, salvo mudança de escopo solicitada. O histórico local é a fonte de verdade; cálculos usam timestamps e snapshots históricos. Ao mudar o formato salvo em localStorage, preserve compatibilidade e só altere `DATA_VERSION` se o schema exigir.
- Mantenha a interface limpa e compacta ativada por padrão, sem ocultar erros, alertas essenciais ou o disclaimer. Use o rótulo **Exportar bebidas**. Exportar/importar bebidas e backup/restauração devem continuar visual e funcionalmente separados.
- Importar bebidas preserva o histórico. Backup inclui bebidas, histórico e preferências; exclui PIN, credenciais, bloqueio e sessão do aparelho. Preserve prévias e confirmação antes de aplicar arquivos.
- Compartilhamento entre usuários, relações entre bebidas, mesclagem e backup criptografado permanecem no roadmap, sem implementação até solicitação. O app acompanha intervalos configurados e não determina segurança para consumo.
- Para alterações de JavaScript, execute `node --input-type=module --check < app.js` (app.js é módulo ES; `node --check app.js` sozinho falha — ver src/README.md) e `node --check sw.js`; complemente com testes manuais pertinentes de DEVELOPMENT.md. Relate os testes executados e os não realizados. Não apague armazenamento real para testar.
- Em releases, confira versão da aplicação, footer, documentação e cache do Service Worker; altere DATA_VERSION somente se o schema exigir. Mudanças apenas documentais não exigem nova versão. Entregue ZIP somente se pedido, com arquivos na raiz.
